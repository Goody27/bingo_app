# 設計判断の記録

実装中に下した判断と、その理由。**なぜ別の案を採らなかったか**も残す。

---

## D-1. ドメインロジックを GenServer から切り離した

**決定** — ビンゴのルールは `Game` / `Card` / `Deck` などの純粋関数に置き、
`GenServer` は状態の保持とイベント配信だけを担当する。

**理由** — ビンゴ判定（12 ライン、FREE マス、同時達成の順位）は最もバグりやすい。
ここが GenServer の中にあると、テストのたびにプロセスを起動し、
メッセージを送り、非同期の結果を待つことになる。

純粋関数なら値の比較だけで検証できる。実際 `game_test.exs` の 38 件は
**プロセスも PubSub も Phoenix も起動していない**。

**代案** — GenServer に直接ロジックを書く。却下。テストが重くなり、
「状態管理」と「ルール」が混ざって責務が読み取れなくなる。

---

## D-2. 操作関数は `{:ok, game, events}` を返す

**決定** — Decide → Evolve → Publish。判断と状態遷移は純粋関数、
配信は GenServer。

**理由** — GenServer が「何を通知すべきか」を知らずに済む。
`execute/2` という 1 つの実行経路にまとめられるので、操作を追加しても
「配信を書き忘れる」ことが起きない。

```elixir
defp execute(game, domain_fun) do
  case domain_fun.(game, DateTime.utc_now()) do
    {:ok, new_game, events} ->
      Publisher.broadcast(new_game.room_id, events)
      {:reply, :ok, new_game, @idle_timeout}
    {:error, reason} ->
      {:reply, {:error, reason}, game, @idle_timeout}
  end
end
```

自動マークを後から入れたとき、1 操作が複数イベントを生むようになったが、
**GenServer も LiveView も無変更**で済んだ。返り値の形が効いた場面。

---

## D-3. 時刻を引数で受け取る

**決定** — `Game.draw_number(game, actor_id, now)` のように `now` を渡す。

**理由** — ドメイン関数の中で `DateTime.utc_now/0` を呼ぶとそこが副作用になり、
「同じ入力なら同じ出力」が崩れる。引数にすれば、テストは固定時刻を渡せる。

**代案** — デフォルト引数 `now \\ DateTime.utc_now()`。却下。
デフォルトで呼ばれた瞬間に純粋でなくなり、「純粋である」という保証が
呼び出し方に依存してしまう。

---

## D-4. 集約の state を外に出さない

**決定** — `GameServer` に `get_state/1` を作らず、読み取りは
`snapshot(room_id, viewer_id)` だけ。返すのは `Snapshot` 構造体。

**理由** — `%Game{}` をそのまま返すと、LiveView 側で

```elixir
game.participants |> Map.put(...)
```

のような「集約の外での状態改変」が自然に書けてしまう。
読み取り専用の別の型を返せば、**外から state をいじる経路そのものが無くなる**。

さらに `viewer_id` を射影の入力にすることで、他人のカードがプロセスの外に出ない。
これは表示上の都合ではなくドメインのルールなので、テンプレートの書き方に委ねない。

---

## D-5. `join` を冪等にした

**決定** — すでに参加済みの `participant_id` での `join` は、何もせず
`{:ok, game, []}` を返す（イベントも出さない）。

**理由** — LiveView はマウントのたびに `join` を呼ぶ。ここが冪等でないと、
リロードするたびにカードが作り直されて、塗った内容も順位も消える。
スマホでうっかり画面を切り替えた程度でカードが変わるのは致命的。

**副作用** — 「1 ブラウザ = 1 参加者」が確定する。同じブラウザの別タブは
同一人物として扱われる。1 台で複数人をテストするならシークレットウィンドウか
別ブラウザが必要。これは受け入れた（[D-10](#d-10-一人一枚を仕組みで強制しない)）。

**代案** — 呼び出し側に「参加済みか判定してから join」させる。却下。
判定と実行の間に別の join が入る隙間ができる。

---

## D-6. 乱数を 2 つの差し替え口に閉じ込めた

**決定** — `Game.new/2` の `:deck` と `:card_factory` で、抽選順とカード生成を
外から差し替えられるようにした。既定値は本番の挙動。

**理由** — `Card.random/0` を集約が直接呼ぶと、集約のテストが非決定的になる。
`Deck` の抽選順と対称に扱い、乱数をこの 2 箇所だけに限定した。

これがあるおかげで「あと 1 つでビンゴ」の状態や「carol だけが当たりカード」
といった状況を、テストで完全に決定的に作れる。

**トレードオフ** — 構造体に関数を持つので、`%Game{}` をそのままシリアライズできない。
インメモリ前提なので許容した。永続化するなら、この口は設定値に置き換えることになる。

---

## D-7. クリックでのマークを廃止し、抽選時に自動で塗る

**決定** — 参加者の「塗る」操作（`mark` API 一式）を削除し、
`draw_number` が全員のカードを自動でマークする。

**理由** — UX 上、毎回 25 マスから探して押すのは面倒。
そして設計上の副産物が大きかった。

以前は「クライアントが送ってきた番号が抽選済みか」をサーバーが**検証**していた。
いまは**塗る経路が抽選しかない**ので、未抽選の番号が塗られること自体が起こりえない。
不変条件が「検証」から「構造」になり、検証コード（`ensure_drawn`）が消えて
むしろ強くなった。

**付随して決めたこと**
- 途中参加者には、すでに引かれた番号をまとめて反映する（追いつきマーク）。
  自動マークだと「後から入った人だけ塗り忘れる」が起きるため
- 全参加者を**参加順**に走査する。Map の列挙順に任せると、同時ビンゴの順位が
  同じ入力でも変わりうる

---

## D-8. ビンゴ達成でそのカードは上がり

**決定** — ビンゴした参加者は以降マークの対象から外れ、順位がその時点で確定する。

**理由** — 順位を付けるゲームなので、上がったあとも塗り続ける意味がない。
`apply_number/4` で `winner?` を見て早期に抜ける。

参加者一覧はビンゴ順（rank 昇順）→ 未達成者（参加順）で並べる。
「誰が何着か」がこの画面の主役なので、達成者を上に集める。
この並び順は表示の関心事なので、ドメインではなく `Snapshot` 側に置いた。

---

## D-9. 認可を集約に置いた

**決定** — 主催者判定を `Game.ensure_host/2` で行い、`start` / `draw_number` /
`finish` は `actor_id` を必須で受け取る。

**理由** — 画面でボタンを隠すのは「表示上の制御」でしかない。
LiveView のクライアントは任意の `phx-click` を送れるので、devtools から
`draw` を投げれば誰でも抽選できてしまう状態だった。

「誰が操作してよいか」はゲームのルールなので、集約が裁定する。

**細部**
- `host_id` 未設定なら誰も通さない（**既定で拒否**）
- 認可チェックは状態チェックより**先**。非主催者に「もう終わっている」などの
  内部状態を漏らさないため
- `actor_id` はセッション cookie 由来なのでクライアントから偽装できない

**代案** — LiveView の `handle_event` でチェックする。
サーバー側なので安全ではあるが、却下。将来 API やスクリプトから呼んだときに
チェックを書き忘れる。認可はドメインの関心事。

---

## D-10. 「一人一枚」を仕組みで強制しない

**決定** — `participant_id` はセッション cookie 由来の `visitor_id` のまま。
複数端末・シークレットウィンドウからの重複取得は防がない。

**理由** — 本当に強制するには身元の確認（ログイン、招待コードの 1 回限り消費）が要る。
身内の余興ビンゴにログインを入れるのは明らかに過剰。

参加者一覧は主催者から全部見えているので、おかしな名前が出ればその場で
口頭で解決できる。仕組みで縛るより安上がり。

| | 現状 |
|---|---|
| リロード・別タブで二重取り | 防げる |
| 同じ人が PC とスマホで別々に取る | 防げない |
| シークレットウィンドウでもう 1 枚取る | 防げない |

**もし必要になったら** — 効果が大きい順に、①抽選開始で参加を締め切る
②主催者によるキック ③同名の参加を弾く。①②で「増やせる窓を閉じる +
出てしまったものを消せる」が揃う。

## D-11. `restart: :temporary`

**決定** — `GameServer` はクラッシュしても再起動しない。

**理由** — 状態がメモリ上にしかないので、再起動しても**空のゲームが
同じ room_id で復活する**だけ。参加者から見ればカードも履歴も消えている。
それは「復旧」ではなく「静かな事故」なので、落ちきらせて
「ゲームが終了した」と見せるほうが正直。

状態を残したいなら、イベントを永続化して再生する設計が別途必要になる。

---

## D-12. 画面更新の経路を PubSub の 1 本に寄せた

**決定** — `handle_event` の中で socket を更新しない。
自分の操作の結果も他人の操作の結果も `handle_info` で受けてから反映する。

**理由** — 戻り値でも画面を更新する作りにすると「自分の画面を更新するコード」と
「他人の画面を更新するコード」の 2 系統ができ、必ずどちらかがズレる。

**副作用** — LiveView テストで `render_submit` / `render_click` の戻り値が
1 つ前の状態になる。反映後を見るには改めて `render/1` する必要がある
（実ブラウザでは直後に diff が届くので問題ない）。
この前提はテストにコメントで残してある。

---

## D-13. 演出は Web 層に閉じ込めた

**決定** — サーバーは `push_event("fx:drawn", %{label: "B7", mine: true})` のように
「何が起きたか」だけを送り、どう派手に見せるかは `assets/js/fx.js` が決める。

**理由** — ドメインイベントに演出の情報を混ぜるとドメインが UI に汚染される。
「B7 が出た」はドメインの事実だが、「金色に光らせる」は表示の判断。

**細部**
- 演出用 DOM は `phx-update="ignore"` で LiveView の管理外に置く。
  差分更新とアニメーションが競合しないため
- 効果音は音声ファイルを持たず Web Audio API で合成する。
  アセット追加もダウンロードも不要で、オフラインでも鳴る
- `prefers-reduced-motion` を尊重して紙吹雪とルーレットを止める

---

## D-14. ルームはインメモリ（DB なし）

**決定** — `Rooms.Store` は Agent の中の Map。Ecto も PostgreSQL も使わない。

**理由** — DDD の層構造を検証するのが主目的で、永続化は本質ではない。
`Rooms` を境界として切ってあるので、ETS や Ecto への差し替えは
このコンテキストの内側で完結する。

**現状の割り切り** — アプリを再起動するとルームは全部消える。
